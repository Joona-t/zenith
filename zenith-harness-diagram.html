Why RALPH is the baseline to beat

RALPH reopens the gap between current state and the original request every session, so it resists false "done" labels. But it re-discovers everything from scratch each loop — expensive — and has no principled stopping rule.

What Zenith keeps & what it adds

It keeps repeated review, but makes the loop adaptive: the orchestrator dynamically allocates workers, testers, reusable skills, replanning, and stopping decisions — recovering RALPH's rigor without paying for open-ended rediscovery.

Every milestone boundary, the orchestrator picks one move

A single orchestrator session owns the plan, worker definitions, tester definitions, reusable skills, validation reports, issue lists, and stopping decisions. It never implements — it delegates. Click a decision to see when it fires.

Runtime lifecycle

The mission is driven only through orchestrator runtime tools — state is durable, so a mission survives context resets and can run for days.

draft→ mission_planning→ mission_running⇄ attention_needed→ done/ failed/ aborted

start_project

No project or a draft → open the mission with a brief and a workspace dir.

submit_plan

In planning: investigate, load the playbook, write the falsifiable contract, author the task list, then submit. Persists state — does not dispatch.

advance_project

In running: dispatch runnable work or evaluate a ready validation gate. Call it again while work remains.

decide_attention

Attention needed: read every open item + its evidence, decide exactly once each, then advance.

end_mission

Quiescent + evidence supports closure → request terminal review. Stops on genuine completion, not agent overconfidence.

abort_project

User-requested or justified cancellation — preserves the task record.

Use it when…

Project-scale builds, repo-scale implementation from scratch, hard multi-session debugging, verification-heavy work, ML/optimization loops, paper reproduction — anywhere premature "done" is the real risk and you want separate workers + independent validators + a durable stopping rule.

Don't use it for…

Tiny edits, single-command tasks, or one-shot answers. The orchestration overhead only pays off when the task needs explicit milestones, parallel worker/tester loops, durable mission state, or an independent final review.
